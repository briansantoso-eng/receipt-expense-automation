# Worked examples

Two kinds of evidence, kept separate so nothing is overstated: **synthetic
receipts you can regenerate and run yourself**, and **six real receipts** with
the output they produced.

---

## 1. Synthetic receipts — reproducible

`bunnings.png` · `cafe.png` · `cloudbase.png` · `fuel.png` · `cafe_blurry.png`

Generated by `make_sample_receipt.py`, so anyone cloning this repo can produce
them and run the pipeline end to end:

```bash
python make_sample_receipt.py
python batch_receipts.py --folder receipts --out expenses.csv
```

They are not decoration — each one carries a specific trap:

| file | the trap |
|---|---|
| `bunnings.png` | prints `SUBTOTAL 47.30` but the ex-GST subtotal is **43.00** — GST is *inside* the total |
| `cafe.png` | never prints a subtotal at all; it has to be derived |
| `fuel.png` | litres × price-per-litre, no subtotal line, GST buried in the footer |
| `cloudbase.png` | **US invoice** — tax is *added* to the subtotal, the opposite of the others |
| `cafe_blurry.png` | same receipt as `cafe.png`, blurred and rotated; should populate `unreadable_fields` rather than invent numbers |

Correct answers:

| file | currency | subtotal | tax | total | tax inside total? |
|---|---|---|---|---|---|
| bunnings | AUD | 43.00 | 4.30 | 47.30 | yes |
| cafe | AUD | 14.09 | 1.41 | 15.50 | yes |
| cloudbase | USD | 49.00 | 4.35 | 53.35 | **no** |
| fuel | AUD | 58.11 | 5.81 | 63.92 | yes |
| cafe_blurry | AUD | 14.09 | 1.41 | 15.50 | yes |

The pipeline gets all five right, including both tax regimes, and flags
`cafe_blurry` rather than guessing silently.

## 2. Real receipts

**[real/](real/)** — all six photos, each paired with the JSON it produced.
`real-receipts-results.csv` is the combined spreadsheet.

Six genuine receipts, photographed on a phone: crumpled, shot sideways, one
food-stained, one legitimately GST-free. **6/6 correct on every total, tax and
date**, verified by reading the originals by eye.

```
date        vendor                  category               subtotal   tax    total   status
2025-09-14  TK Maxx                 supplies                  47.25   4.72   51.97   check
2025-09-14  Thai Kee IGA S/Market   supplies                  26.41   2.64   29.05   ok
2025-09-14  Thai Kee IGA S/Market   supplies                   4.45   0.00    4.45   check
2026-02-23  Coles                   supplies                  12.09   1.21   13.30   ok
2026-04-22  TK Maxx                 supplies                   7.26   0.73    7.99   ok
2026-08-10  LL Anderson Bros        professional_services    126.36  12.64  139.00   check
```

The three `check` rows are worth understanding, because none of them is an error:

- **Thai Kee, $4.45** — `tax 0.00` is correct. The receipt prints
  `TRANSACTION INCLUDES GST: $0.00`; the item was fish sauce, and basic food is
  GST-free in Australia. Flagged because zero GST on an AUD receipt is unusual
  enough to be worth three seconds of a human's attention.
- **TK Maxx, $51.97** — the GST line sits on a crumpled fold. Flagged as guessed;
  the value was right anyway.
- **LL Anderson, $139.00** — the docket states `Amnt Paid` and `Pre-Paid Cards`
  but never a card type, so `payment_method` was genuinely ambiguous.

Nothing incorrect was ever returned unflagged. That property matters more than
the accuracy rate: a wrong number nobody questioned is far worse than a right
number that got double-checked.

### The photos

**[real/](real/)** has all six, each paired with the JSON it produced.

Card numbers, staff names, a phone number and other customers' receipts caught
in frame are blacked out. Every redaction was checked by eye afterwards — one
pass missed a bystander receipt visible at the edge of frame 4, which is why the
verification step exists rather than trusting a single run.

The `payment_method` and `source_file` columns are dropped from the CSV and the
JSON for the same reason. Everything else is untouched output.
